# 2026-09-17 — The core owns the Cloudflare quick tunnel next to the public listener

- **Context:** The app's Remote access feature puts a Cloudflare quick tunnel (`cloudflared tunnel --url <origin>`) in front of the Local API Server: a temporary public `https://<words>.trycloudflare.com`, no account, a new name on every start. In the app it was a Rust manager inside the process that also ran the proxy (`remote_access/`). On the core-migration line the core serves `:1337` and owns the Host gate, so the tunnel's two obligations — trust the tunnel name only while the tunnel is up, and never leave a public URL pointed at a port that has stopped or changed — can only be kept by whoever owns the listener.
- **Decision:** `src/remote-access/` holds the manager: phases `off | starting | online | stopping | error`, a monotonic `run` so an overtaken supervisor can no longer write state, injected spawner, prober and timings (15 s to register, 45 s to answer, 5 s + 5 s to stop). A URL alone is never ready: `cloudflared` must also print `Registered tunnel connection`; a URL without a registration retries once over `--protocol http2` (networks that drop QUIC), no URL at all does not. The tunnel name is trusted *before* the probe and cleared on every end. The URL is shown only after it answers as this server. Status is the app's camelCase shape verbatim, pushed as `remote-access:status`; routes `GET /atomic/v1/remote-access`, `POST …/start` (answers `starting` at once), `POST …/stop` (answers once the process is gone). Refusals are 409 `REMOTE_ACCESS_SERVER_STOPPED | _OPERATION_IN_PROGRESS | _STOP_FAILED` with the app's lowercase reason in `details`. Ordering lives in `PublicServerLifecycle`: a public stop ends the tunnel first; a genuine start ends a surviving tunnel (it pointed at the previous port) and announces; an idempotent start touches nothing; core shutdown kills the tunnel synchronously as its first statement. The API key is deliberately not a precondition. The binary is not downloaded by the core: `--cloudflared-bin`, then `ATOMIC_CLOUDFLARED_BIN`, then `<resources-dir>/cloudflared[.exe]`; none means `cloudflared_unavailable`. Arguments are the app's: `--config <empty>` (`/dev/null`, or an empty file under `<data>/atomic-core/` on Windows) so a user's own named-tunnel ingress rules cannot 404 the quick tunnel, `--no-autoupdate`, every `TUNNEL_*` variable scrubbed.
- **What replaces the Rust-only mechanisms:** `kill_on_drop` → `killNow()` first in `shutdown()` plus a `process.once('exit')` hook while a child is alive. `PR_SET_PDEATHSIG` and the pid journal → `<data>/atomic-core/remote-access-tunnel.json` `{pid, process_start_id, instance_id, exe}`, written right after spawn; at startup, before the endpoint is published, the recorded process is killed only when its start identity matches *and* its name starts with `cloudflared`, so a user's own tunnel is never touched. An app owner that loses its client shuts down within its lease, which kills the tunnel. A separate process group is deliberately not replicated: staying in the core's group means a group kill takes the tunnel down too, the safe direction for public ingress.
- **Consequences:** a core crash leaves the tunnel up until the next core starts on that data folder (the Rust app had the same gap outside Linux). A public stop can take up to ~12 s when `cloudflared` ignores signals; shutdown is unaffected. `cloudflared`'s output and the tunnel URL are never logged or persisted by the core. Remote-access status is not part of the control snapshot: clients read `GET /remote-access` when they attach, on focus and on server transitions, as the app already does.
