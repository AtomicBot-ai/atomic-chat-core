# 2026-10-06 — vLLM runs `vllm serve` with its KV cache in bytes and its memory share sized by core

- **Context:** change `add-vllm-runtime` adds vLLM (`docker.io/vllm/vllm-openai:v0.31.0`, pinned by digest in `runtimes/vllm.json`) as a second managed engine. vLLM V1 sizes its memory as a share of the card's *total* memory (`--gpu-memory-utilization`) and, before it starts, refuses to run when the card's free memory is below that share — so a fixed share fails on any desktop whose card holds a display and a browser, which is exactly the user TensorRT-LLM does not reach. vLLM also sends usage stats and may reach Hugging Face by default.
- **Decision:** the `vllm` adapter (`src/runtime/vllm/adapter.ts`) runs `vllm serve <model> --served-model-name <id> --host 0.0.0.0 --port 8000 --max-model-len <ctx> --max-num-seqs <n> --gpu-memory-utilization <U> [--kv-cache-memory-bytes <B>] --limit-mm-per-prompt {"image":0,"video":0}`, with `--enforce-eager` when CUDA graphs are off (`auto`: below 12 GiB of card), `--kv-cache-dtype fp8` on compute capability 8.9+, and the family's parsers; never `--trust-remote-code`, `--enable-log-requests` or `--api-key`. Its env switches usage stats off and Hugging Face offline and puts every compile cache under the engine cache. `U` is core's (`src/runtime/vllm/memory.ts`) unless the `gpu_memory_utilization` setting fixes it: auto gives `min(0.95, (free − 1.5 GiB) / total)` of the card re-probed right before the container (half the host's memory at most on unified memory). Within `U` vLLM sizes the KV cache itself — it knows every model's KV shape, hybrid ones included; `--kv-cache-memory-bytes` is passed only when the `kv_cache_memory_gib` setting fixes it. History, from the Windows acceptance (2026-10-06, RTX 4070 Laptop under WSL): core first sized the KV cache in bytes from the attention layers only, which gave Qwen3.5 (linear attention in three layers of four) a third of what vLLM needs, so every load failed; and the first margin of the share, 512 MiB, was smaller than vLLM's own CUDA context (0.87 GiB), which already holds memory when vLLM checks the share, so every start failed too. The managed-text lifecycle now runs `beforeCreate` once right after `stopPrevious` and hands what it answers to `buildLaunch` as the engine's `plan`, so the card is re-probed after the previous sessions stopped. Weights + an estimate of the KV cache + ~2 GiB of engine overhead are checked against the free memory before any container, by the same rule as `POST /models/vllm/check`.
- **Consequences:** vLLM's own start check passes on a partly used card as long as its CUDA context stays under the 1.5 GiB margin; its failure is classified as out of memory with both numbers; a model that does not fit is refused with numbers before a container exists. The overhead (2 GiB), the margins (512 MiB in the memory check, 1.5 GiB in the share), the readiness timeout (10 min + 20 s/GiB), the stage markers and the exit wording are first estimates from vLLM 0.31's source; the live run of task 6.1 (`test/live/vllm.test.ts`) confirms or changes them with the numbers recorded in the change's rulings.
