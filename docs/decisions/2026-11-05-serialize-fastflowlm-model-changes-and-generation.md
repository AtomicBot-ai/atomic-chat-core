# Serialize FastFlowLM model changes and generation

The owner persists approved driver operations and client model maintenance in separate journals. An approved host step can outlive its requesting UI. The owner consumes the bound receipt before probing XRT and uses a boot identity to distinguish an owner restart from an interrupted system transaction.

Engine changes, model loads and maintenance share one owner lock. The owner persists the model guard before releasing a resident process and checks the guard before returning even an existing session. The client can finish its own installation journal after a crash. A partial model keeps the guard until the installer repairs or rolls back the directory.

Each session runs one managed executable, independently of GPU residency. A keyed gateway serializes generation and admits four waiting calls. After a client disconnects, the gateway closes the upstream connection and sends an empty JSON chat request directly to that backend. The pinned FLM server takes its generation lock before dispatching chat, and the local-only handler rejects the empty request before inference. Its specific rejection acknowledges that the previous handler released the generator. A three-second deadline bounds the wait. On failure the owner terminates only its own child and the process journal reports session death.
