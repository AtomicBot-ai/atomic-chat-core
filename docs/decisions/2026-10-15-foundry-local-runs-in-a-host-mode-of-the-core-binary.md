# 2026-10-15 — Foundry Local runs in a hidden host mode of the core binary, one process per model

- **Context:** Microsoft Foundry Local v2 (MIT) is a native library, not a program: `foundry_local` plus ONNX Runtime and ONNX Runtime GenAI, a versioned C API (`foundry_local_c.h`, `FOUNDRY_LOCAL_API_VERSION` 2) and an OpenAI-compatible server that starts inside whichever process loaded it, with no authentication. Its `foundry` CLI is under an EULA that forbids embedding. Loading the library into the core would let a native crash take down the core and `:1337`; a separate program in the app would split the host, its protocol and its caller across two repositories and releases. Change `add-foundry-local`, design D1; spike results in its `rulings/core.md` (S1, S2).
- **Decision:** the host is a hidden mode of the same binaries, `atomic-chat-core foundry-host probe|prepare|serve` (and `atomic-chat-app-core foundry-host …`), started by the core with `process.execPath`, one process per model. `src/runtime/foundry-local/host/ffi-bun.ts` binds the C API's function tables over `bun:ffi`; it is the only file in `src/` allowed to import `bun:*` — allow-listed in `scripts/check-runtime-agnostic.mjs` and in ESLint's `no-restricted-imports`, imported only dynamically by the host mode, with its own minimal type declarations (`host/bun-ffi.d.ts`, no `@types/bun`). Under Node the mode fails with a clear error; the npm package still loads. The session is the core's gateway on its own loopback port (Bearer key + Host), which forwards `/v1/chat/completions` and `/v1/models` to the host under `/catalogs/local` and renames the model between the core's id and the registration id `<id>:1`.
- **Consequences:** a library crash ends one host; the core reports `session:died`. What the spike proved and the host relies on: progress callbacks must not be `threadsafe` (the library calls them on the calling thread for CDN accelerators, never for Windows ML ones); on Windows the library's dependencies load only after `SetDllDirectoryW(<lib>)`; models registered with `RegisterModel` are served under `/catalogs/local` and only by their full `<name>:<version>`; the `execution_provider` metadata wants the catalog spelling (`WebGPUExecutionProvider`). Two shared mechanisms grew an option, unchanged for every other caller: `SpawnSpec.stdin: 'pipe'` keeps the host's stdin open, and on Windows (no SIGTERM) `terminate` closes it and waits before killing; the session gateway's upstream may carry a `basePath`. Windows arm64, the notarized macOS app and an NPU on a Core Ultra machine are still to be run before the release (6.8 gates); a failure there reopens this decision for that platform — the fallback is a small C host in this repository speaking the same protocol.
