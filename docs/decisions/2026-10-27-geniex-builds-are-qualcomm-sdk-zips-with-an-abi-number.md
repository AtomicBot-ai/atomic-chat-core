# 2026-10-27 — GenieX builds are Qualcomm's SDK zips from its S3 mirror, gated by our own ABI number, with the HTP bundle loaded from the build folder

- **Context:** Qualcomm publishes `geniex-sdk-windows-arm64-<tag>.zip` (about 92 MB) on GitHub Releases and on an S3 mirror (`qaihub-public-assets.s3.us-west-2.amazonaws.com/qai-hub-geniex/`) with a per-tag `manifest-<tag>.json` naming each asset's sha256. The zip holds `lib/geniex.dll`, the `llama_cpp` and `qairt` plugins, QAIRT and the Microsoft-signed HTP files (`libggml-htp-v*.so`, `.cat`, `.inf`), plus `bin/` and `include/` we do not need. GenieX is pre-1.0 and changes its header with minor versions. Its CLI installer is the alternative: system-wide, unsigned, no version control from the core. Change `add-geniex-runtime`, design D2 and D3.
- **Decision:** `geniex` is an `engine-builds` engine like LiteRT-LM: conf's `backends/geniex-manifest.json` lists releases with an explicit zip URL on the S3 mirror or a `qualcomm/GenieX` GitHub release (nothing else is accepted), `size` and `sha256`, `min_core_version`, and `abi` — a number of ours that moves when the functions and structs `ffi-bun.ts` reads change (`SUPPORTED_GENIEX_ABI`). An install keeps only `lib/**` of the zip, without its top folder, probes the staging tree with `geniex-host probe --lib <staging>` of this very core, records the devices the library found (`HTP0`, `GPUOpenCL`, `CPU`) in `install.json`, and only then swaps it in; the active build is the newest by `published_at` with a bound ABI. The provider registers on Windows arm64 whose processor string names a Snapdragon X Elite (`X1E`) or X2 Elite (`X2E`) only; the chip decides which AI Hub bundle fits. The HTP bundle is loaded from the build folder beside `ggml-hexagon.dll`, with no driver install, administrator rights, reboot or test signing — what the spike's S1 must confirm; `GET /runtimes/geniex/accelerators` answers from the recorded devices without a new probe, and `prepare` has nothing to do.
- **Consequences:** no mirror and no release pipeline of our own; the sha256 in conf pins Qualcomm's file, and a deleted asset leaves installed builds working. A new GenieX release with changed signatures needs a core release and a new `abi` before conf may list it. Should the DSP accept the signed `.so` files only from the driver store, the operator's decision (task 3.6) is to drop the change or add a driver-install step under UAC as a separate decision; nothing in the install path assumes either. A machine without the Qualcomm NPU driver installs fine and lists `gpu` only, with `npu` variants judged `accelerator-unavailable`.
