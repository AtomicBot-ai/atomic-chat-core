# 2026-09-17 — Cancel a model load through a shared per-model registry outside the transition queue

- **Context:** The app's image-generation line let a user cancel a model load: a multi-gigabyte load over a cold page cache can take minutes, and until the server reported ready nothing could stop it (app ADR `2026-09-15-say-what-a-model-load-is-waiting-on-and-let-it-be-cancelled`). That lived in the Rust plugins the core migration removed (`utils/src/load_cancel.rs`, the three plugins' `cancel_*_model_load`). The Rust registry replaced a model's token on every new load ("replace, don't trip"). In the core that rule would miss: `LocalSessions.withModelTransition` serializes acquires of one `provider\0modelId`, so the newest registration is always a queued follower and a cancel would never reach the load that is actually spawning. A second control request for the cancel would also queue behind the very load it wants to stop.
- **Decision:** `POST /atomic/v1/models/:provider/*modelId/load/cancel` answers `{cancelled}` and runs outside the transition queue. `LoadCancelRegistry` keeps one shared entry per key for every pending acquire and starts a fresh generation only after an abort, so a later load never inherits an earlier cancel. The signal reaches the runtimes as `LocalLoadOptions.signal` and the spawn as a separate `ReadyOptions.cancelSignal`: a user cancel kills the child at once and raises `MODEL_LOAD_CANCELLED` (409, "The model load was cancelled.", the app's code verbatim) only after the exit is confirmed, while the owner-shutdown signal keeps `CORE_NOT_RUNNING`. Checkpoints: before spawn, during readiness, after readiness before the session is published, and while queued behind another load of the provider. A cancel that races readiness still wins until the acquire's answer is decided; afterwards it answers `false` and the caller unloads. A `signal` key in the request body is ignored. Load stages (`installingEngine`, `loadingWeights` with the page-cache fraction) stay in the app: `mincore` has no runtime-agnostic equivalent, and the app already owns that step.
- **Consequences:** A cancelled load frees its memory before the error reaches the caller, releases the model claim only when no process is left, and never falls into the projector or MTP retry. Every acquire waiting on the same model is rejected by one cancel; a core-initiated reload (context growth, recovery) carries no signal and is not cancelled, though an acquire that joined it is. A cancelled queued load must not let the next load overlap the one ahead, so the runtime queues chain on both the turn and the result. Deliberate difference from the Rust registry: shared entry instead of replacement; the five Rust test semantics still hold and are ported.
