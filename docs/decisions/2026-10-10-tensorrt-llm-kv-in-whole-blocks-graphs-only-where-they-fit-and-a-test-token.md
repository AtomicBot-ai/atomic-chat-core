# 2026-10-10 — TensorRT-LLM asks for whole KV blocks, captures CUDA graphs only where they fit, and must generate one token before it is ready

- **Context:** on the RTX 5090 Laptop (Windows, WSL, 24 GiB) two different failures both reached the user as "Not enough memory to load the model".
  1. With `context_length` 2096 every model was refused with 17 GiB free. The launch wrote `kv_cache_config.max_tokens: 2096`; `trtllm-serve` 1.3.0rc29 keeps whole 32-token blocks and rounds down — 65 blocks, `max sequence length=2080` — and `classifyTensorrtLlmReady` refused 2080 < 2096 as out of memory. Any context that is not a multiple of 32 failed the same way at batch 1; at batch N the bound `context × N` could hold one block fewer than N full sequences need.
  2. `NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4` with `cuda_graphs: auto` passed the memory check (23.4 GiB needed of 23.57 free, [2026-10-09](2026-10-09-tensorrt-llm-memory-check-counts-the-engines-weight-layout.md)), answered `/health`, and failed every request with "CUDA out of memory … 0 bytes is free": 26.37 GiB peak against 21.47 GiB with graphs off (5.15 GiB outside torch instead of 1.92, 2.57 GiB of activations instead of 1.32). `auto` kept graphs on any card of 12 GiB or more, the check never counted them, and the hybrid model's cache manager (V2) logs no `max sequence length=` line for `classifyReady` to read — it said `setting max_seq_len to 672` and, on the next line, `max_seq_len=2048`.
  The load failures also left nothing in `core.log`: the last attempt's log lived only in memory, and the container's own log went with the container.
- **Decision:**
  - `kv-cache.ts`: `TENSORRT_LLM_TOKENS_PER_BLOCK` 32 (the image's default `tokens_per_block`, not written to the YAML: a key this image does not know would fail every launch). The launch asks for `batch × ceil(context / 32) × 32` tokens; an explicit `kv_cache_max_tokens` is rounded up to whole blocks; the unified-memory bound counts blocks per context the same way. The readiness check is unchanged: relaxing it to the rounded-down length would start an engine whose `max_seq_len` is shorter than the context the session gateway admits.
  - `cuda-graphs.ts`: `TENSORRT_LLM_CUDA_GRAPHS_RESERVE_BYTES` 5 GiB, the Nemotron difference rounded up (about 2 GB on an 8 GB card for Qwen3.5-2B). `cuda_graphs: on` adds it to the memory check (`cuda_graphs_bytes`), so the check refuses rather than starts a model that cannot answer. `auto` adds nothing to the check; instead `tensorrtLlmLaunchPlan` (the engine's `launchPlan`, run in `beforeCreate` on the card as it stands after eviction) keeps graphs only when the free memory beyond the check's own need is at least the reserve, still on a card of at least 12 GiB or a unified-memory one. Without a plan the launch falls back to the card's size alone.
  - `ManagedTextAdapter.generationProbe` (managed-text): once an engine is ready and `classifyReady` passed, the lifecycle reads the model's name off `GET /v1/models` and POSTs one non-streamed token of chat straight to the engine. An error answer (non-2xx, or an `error` object in a 2xx body) fails the load, classified by `classifyExit` over the log tail (`OUT_OF_MEMORY` for the CUDA message), with the HTTP answer in the details. No answer within `generationProbeTimeoutMs` (120 s), no model name, a redirect or no connection is not proof either way: the load proceeds with a warning. TensorRT-LLM declares the probe; vLLM does not yet.
  - `failLoad` writes one line to the core log — `loading <model> failed: [CODE] message` and the classification's excerpt — not the engine's output, which runs to hundreds of lines per start.
  - The app's out-of-memory toast keeps its generic copy and now carries the core's sentence and the log under "Show details", as the other load failures already did.
- **Consequences:** a context that is not a multiple of 32 now loads; the engine holds up to 31 tokens more KV per sequence than the context. Nemotron-class checkpoints on a 24 GB card start without CUDA graphs under `auto` and decode somewhat slower; with `on` they are refused by the check. Every TensorRT-LLM load spends one generated token (and up to 120 s when the engine does not answer) before it is ready. The probe cannot catch an engine that generates one short token but fails at long prompts — the KV line check still covers that for attention-only models — nor a WDDM spill, which answers slowly rather than with an error. The 5 GiB reserve is two points of measurement and, like the weight-layout allowance, should be re-measured with each new engine image; so should the block size.
