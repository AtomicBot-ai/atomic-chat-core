# 2026-10-15 — Foundry Local's accelerators are prepared only when a client orders it

- **Context:** the Foundry Local library finds and downloads its execution providers itself: NPU plugins (OpenVINO, QNN, Vitis AI, TensorRT-RTX) through Windows ML, CUDA and WebGPU from Microsoft's CDN, into `<app_data_dir>/ep`. CUDA is about 2 GB on Windows. Left to the library, a model load would download for minutes with no progress the app can show. The library also forgets what it registered when its process ends, and its C API reports no reason for an accelerator it could not register — only its log does. Change `add-foundry-local`, design D3.
- **Decision:** nothing downloads an accelerator on its own — not the start, not an install, not a model load. `GET /atomic/v1/runtimes/foundry-local/accelerators` answers the last `foundry-host probe` of the active build (probed when first asked, when the active build changed, after a prepare, or with `?force=1`). `POST …/accelerators/prepare {accelerators?}` runs one `foundry-host prepare` at a time (`ENGINE_INSTALL_IN_PROGRESS` for a second), one library call per accelerator so a failure stops nothing else, publishes each step as `foundry-local:accelerators` and answers the summary. What is prepared is the core's own record, `<data>/foundry-local/runtime/accelerators.json`; a failure's reason comes from the library's log. A load whose accelerator is not prepared is refused with `FOUNDRY_LOCAL_ACCELERATOR_NOT_PREPARED` before any process starts; `serve` registers only the variant's own, already prepared accelerator.
- **Consequences:** the app shows a prepare step with its size and progress, and a refusal it can explain. Windows ML accelerators report no progress, so their events carry `fraction: null` until `done`; and Windows ML installs its plugins as MSIX packages, which a non-interactive session (SSH, a service) cannot do the first time — the desktop app runs the core in the user's session, `atc` as a Windows service would not prepare them. The compatibility check (`POST /models/foundry-local/check`) reads the same record and the hardware's NPU answer (`probeNpu`), since Windows ML offers OpenVINO on machines without an NPU.
