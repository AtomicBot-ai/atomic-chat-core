# 2026-11-10 — Prepare Foundry macOS WebGPU through ORT

- **Context:** Foundry 2.4.0 installs on macOS ARM64, but its native `Manager_DownloadAndRegisterEps` fails with `unknown error` after extracting WebGPU 0.2.1. A typed C++ client reproduces the failure without Bun FFI. The unchanged provider registers through standard ORT API 31 and generates through Foundry 2.4.0/GenAI 0.19.0. This resolves the Mac acceptance limitation recorded in the Foundry upgrade ADR.
- **Decision:** Only for macOS ARM64/runtime 2.4.0, explicitly prepare and register the same Microsoft CDN provider. Reuse the core downloader and regular-file archive extractor, pin both ZIP and dylib sizes/SHA-256, and atomically cache the original library under `foundry-local/runtime/v2.4.0/macos-arm64/webgpu-ep/0.2.1/`. Register it on ORT's shared environment and hold that reference until after the manager and its sessions are released. Report registered only after the real call succeeds. Await asynchronous preparation before emitting readiness or loading a model. Permit downloads only in `foundry-host prepare`; `serve` validates and reuses the cache, with an instruction to prepare again if it is missing or modified.
- **Alternatives:** Retrying native preparation repeats the same failure. Ignoring it and marking the accelerator prepared does not register a usable provider. Mutating Microsoft's private `active` pointer couples our preparation to its bundle lifecycle; 2.1.0 can remove unreferenced generations from that shared directory. The separate build cache avoids that coupling. Changing ORT/GenAI, signatures or published runtime archives is unnecessary.
- **Consequences:** First preparation downloads 3,447,797 bytes; the installed library is 10,432,384 bytes. A changed CDN artifact fails integrity checks instead of silently replacing native code. Each model host verifies the cached dylib and registers it again without fetching. CPU, 2.1.0, other platforms and future runtime versions retain their existing paths. The internal manager method may now return a promise; its synchronous implementations remain supported. Disk failures retain `[disk_*]` tags. Signed desktop application qualification remains a separate consumer check.
- **Evidence:** Ordinary compiled core: prepare → load Qwen3.5 0.8B WebGPU → streamed public `/v1/chat/completions` answer → unload, with all 13 original model-file hashes unchanged. Targeted compiled app-core also prepares and generates from a fresh host; a separate case refuses an unprepared model without creating/downloading an EP cache. Unit tests cover deferred registration, failures, scope, cache reuse, both hash boundaries, tampering, repair and disk errors.
