# 2026-10-10 — The terminal patch is ported, and everything it changes for the app is opt-in

- **Context:** `atc` (`eye-cli`) ran on `atomic-chat-core-0.11.2-terminal.3.tgz`, v0.11.2 plus a patch whose source exists nowhere ([terminal-patch-port.md](../terminal-patch-port.md)). Its four features — a public API keyring, parallel range downloads, active downloads in the control snapshot, bounded remote GGUF inspection — had to land in `src/` before `atc` could move to a current core. The app runs the same core, so the port must not change what the app sees. Recovering the compiled diff showed three changes that did, unconditionally: download progress also every 250 ms by wall clock (the app's bar is fed every 10 MiB on purpose, see `the progress cadence the app draws its bar from`); a 20 s limit on reading a remote GGUF header, which the app's model setup reaches through `planFor` (`inspectRemote: true`) and would then plan without the header on a slow mirror; and a byte-budget failure thrown as a plain `Error` instead of `GgufParseError`.
- **Decision:** rewritten in TypeScript against `src/`, not copied:
  - `AtomicCoreOptions.publicApiKeys`, read for every public request (`configFor`): `undefined` keeps `server.api_key`, a list replaces it, `[]` refuses everyone, an empty entry matches nothing. `requires_api_key` (state, state file, tunnel endpoint) is the listener's own answer. `hostAndKeyGate`'s new `apiKeys` is optional, so the managed session gateway is unchanged.
  - `AtomicCoreOptions.downloadStreams` → `DownloaderDeps.streams`: a hash-pinned file of at least 32 MiB over up to 4 bounded ranges (`downloads/segmented.ts`), each in its own file under `<path>.segments/` keyed by URL, size, hash and stream count, retried with the downloader's own backoff, a range idle for 120 s retried as a stall, falling back to one stream when the server cannot serve ranges. Verification stays the downloader's, after every file. A cancelled parallel download reports `Download cancelled`. The 250 ms progress cadence comes only with `streams` > 1, on the injected clock `DownloaderDeps.now`.
  - `Downloader.snapshot()` → `GET /snapshot` `downloads`: every running task's last `download:progress` payload, zeros before its first. A superseded run never writes into its successor's entry.
  - `inspectRemoteGguf` reads from 64 KiB, doubling (`readGgufTensorSummaryChunked`'s new `growth: 'doubling'`), within 64 MiB, and still throws `GgufParseError` past the budget. Its time limit is `AtomicCoreOptions.remoteGgufTimeoutMs`, unset by default: the app keeps waiting, `atc` sets 20 000. A timed-out read says so instead of surfacing an `AbortError`.
- **Consequences:** a core created without the new options behaves as before, except that a remote GGUF header is fetched from 64 KiB doubling rather than 4 MiB at a time — one request for a small header, a few more bytes for a large one. `atc` keeps what the patch gave it only by passing `publicApiKeys`, `downloadStreams: 4` and `remoteGgufTimeoutMs: 20000` explicitly; the patch hard-coded the last. The snapshot's `downloads` entries are camelCase like the `download:progress` event they repeat. Not covered: a live mirror under real latency, and `atc`'s own contract tests against this core.
