# 2026-11-06 — Measure Windows AMD UMA per adapter

- **Context:** Windows CIM reported the Radeon 860M framebuffer as 512 MiB. Backend selection consequently preferred CPU despite available shared GPU memory. DXGI also reports shared-system capacity for discrete GPUs, so that number alone is not evidence of UMA.
- **Decision:** Extend the existing bounded PowerShell hardware probe with DXGI adapter capacities and D3D12 architecture UMA evidence. Match exact PCI vendor/device/subsystem identity, reject ambiguous matches, and expose shared capacity only for AMD adapters with an affirmative UMA result. Keep dedicated and shared MiB separate; capacity uses their maximum, never their sum. No CPU-name or half-RAM estimate is used.
- **Consequences:** Upstream llama.cpp, TurboQuant and Prism can recommend GPU builds for measured UMA adapters while retaining their existing capacity thresholds and backend support gates. Vulkan eligibility requires sufficient capacity on the same Vulkan adapter. Linux HIP eligibility remains independent of a Vulkan ICD. Missing native APIs or blocked Add-Type leave shared memory unknown; existing CIM/registry facts remain available. Capacity is not a promise of free memory or successful model allocation.
- **Alternatives:** Treating every AMD GPU as UMA, using a small framebuffer as proof, or attributing shared memory to a whole Ryzen machine would inflate discrete-card capacity in hybrid systems. Installing a hardware-detection dependency is unnecessary; the Windows APIs run inside the existing probe process.
