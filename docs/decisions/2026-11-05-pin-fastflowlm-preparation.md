# Pin FastFlowLM preparation to the measured owner and qualified recipe

A successful native probe establishes readiness offline on any supported host. For a failing probe the owner reads local platform facts before resolving the environment manifest. Automatic preparation requires one supported device, a known owner identity, a matching qualified build and a recipe for the running platform. Linux also requires a writable Ubuntu installation and an exact kernel match. Inconclusive measurements leave the plan blocked. Each proposed change identifies the dependency or account setting it would affect. A denied DRM node prevents native measurements until the account gains access. Low memlock can prevent even a healthy XRT library from opening a device, so a scoped limit change precedes any package plan in that case. An isolated system XRT failure offers only pinned userspace packages.

The provider cache keeps validated manifests by canonical SHA-256 in an atomically replaced history, separately tracking the latest document for each override URL. A new configuration may withdraw recipes for new plans. Keeping previous documents lets an approved operation recover its exact inputs across a restart. Reusing a manifest ID or recipe revision for different contents is rejected. The cost is cache growth with each publication.

The plan digest includes the displayed changes, pinned dependencies, host, device, build and runtime identity. The approval check compares a freshly computed actionable plan with the supplied digest. Executing changes and persisting the operation are separate steps.
