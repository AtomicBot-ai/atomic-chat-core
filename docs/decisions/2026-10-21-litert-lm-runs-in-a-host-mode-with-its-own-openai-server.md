# 2026-10-21 — LiteRT-LM runs in a host mode of the core binary with its own OpenAI server

- **Context:** Google's LiteRT-LM is a native library with a C API (`litert_lm_*`, 212 functions) and no desktop program; its Python `litert-lm serve` holds one model and one conversation and needs Python on the machine. Loading the library into the core would let a native crash take down `:1337`. Unlike Foundry Local, the library has no HTTP server of its own, and its stream callback runs on a C++ thread of its own that frees each chunk as soon as the callback returns. Change `add-litert-lm-runtime`, design D1 and D5; spike results and decision 3.6 in its `rulings/core.md` (S1–S5).
- **Decision:** the host is a hidden mode of the same binaries, `atomic-chat-core litert-host probe|inspect|serve` (and the app core's), started by the core with `process.execPath`, one process per model, as for Foundry Local. `src/runtime/litert-lm/host/ffi-bun.ts` binds the C API over `bun:ffi` and is the second file in `src/` allowed to import `bun:*` (both runtime-agnostic gates list it). Streaming goes through a small C shim the host compiles at start with the TinyCC built into Bun (`cc` from `bun:ffi`, `-nostdlib`, libc and the mutex passed in as pointers): it copies each chunk on the library's thread into a FIFO under a mutex, and JavaScript drains the FIFO on a 2 ms timer while a generation runs. The host serves `/v1/models` and `/v1/chat/completions` itself (stream and non-stream, tools, JSON schema, thinking as `reasoning_content`, images, `stop`, usage), one generation at a time in arrival order, with up to four conversations kept warm; the session is the core's gateway (Bearer key + Host) in front of it.
- **Consequences:** a library crash ends one host and the core reports `session:died`. A `threadsafe` `JSCallback` alone is not an option: it only queues the call, so JavaScript read freed chunks, and even with the chunk copied first it crashed Bun in about one full run in five on a fast GPU stream (7 of 32; 0 of 27 with the FIFO). The shim makes TinyCC part of what has to work on every platform; `probe` compiles it, so a machine where it does not work fails the engine install, not the first load. TinyCC with `SRWLOCK` and `ucrtbase.dll` works on Windows x64 (verified 2026-10-22 on CPU, an NVIDIA GPU and an Intel iGPU), so no shim DLL is needed; the OpenVINO `PATH` for the NPU stays unverified. On Windows the host also leaves EcoQoS, which otherwise keeps a windowless process on efficiency cores (CPU decode 6 → 28 tok/s). Requests to one model queue rather than run in parallel; for server load the managed engines exist. A cancelled conversation cannot be continued (the library answers `CANCELLED` forever), so the pool drops it.
