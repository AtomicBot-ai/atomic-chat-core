# 2026-10-29 — audio.cpp builds come from the Atomic fork through conf's mirror, as the engine-builds row audio-cpp

- **Context:** upstream audio.cpp releases `vX.Y.Z` roughly weekly, mostly from one author, with prebuilt archives for macOS, Windows x64 and Ubuntu x64 only — none for Linux or Windows arm64 — and without eSpeak-ng, which Kokoro needs (every Kokoro speech request answers `Could not load eSpeak-ng`). sd.cpp went the same way: first conf mirrored upstream (2026-09-10), then the Atomic fork built every archive (ADR 2026-10-07, the core owns sd.cpp and MLX engine builds).
- **Decision:** `audio-cpp` is an `engine-builds` engine. `AtomicBot-ai/audio.cpp` builds every archive from an unmodified upstream tag plus `atomic/patches/` (`release-atomic.yml`), named `audio-<tag>-bin-<backend>.zip`, flat, with `-DAUDIOCPP_DEPLOYMENT_BUILD=ON` and without eSpeak-ng: it is GPL-3.0-or-later, and linking it in would make `audiocpp_server` a GPL combined work, so the server stays Apache-2.0 (`static_espeak` stays an off-by-default switch of the fork's workflow). conf's `mirror-audiocpp.yml` signs and re-hosts them and writes `backends/audiocpp-manifest.staging.json`; `audiocpp-approve.yml` moves a checked tag to the live `backends/audiocpp-manifest.json`, which the core reads (`ATOMIC_AUDIOCPP_MANIFEST_URL` overrides it). The manifest has sd.cpp's shape, so the core parses both with one parameterised ggml release parser (`parseGgmlReleaseManifest` with per-engine tag pattern and default repository). Tags are `vX.Y.Z` or a rebuild `vX.Y.Z-a<rev7>`, ordered by version with the rebuild above the bare tag. The host's build comes from sd.cpp's ladder without ROCm; failed rungs are remembered per engine (`<data>/audio/failed-backends.json`). The probe runs `--version` (the binary is audio.cpp) and, for a GPU build, `--list-devices` (it sees a GPU), so a Vulkan build on a machine without a driver moves the install down the ladder. The `backends:` line of `--version` is not trusted, because a build that loads its GPU backend at run time lists only `cpu` there.
- **Consequences:** until the fork's first release is mirrored and approved, conf has no live audio.cpp manifest and the catalog answers "manifest unavailable"; the staging manifest can point at upstream's own archives to bootstrap (no eSpeak-ng, no arm64). Without eSpeak-ng the models that phonemize with it — Kokoro, Piper, SanoTTS, Inflect — answer every speech request with `Could not load eSpeak-ng`, so the catalog offers speech models that need none (MOSS-TTS-Nano, Qwen3-TTS), and the fork's smoke and the core's live tests speak with MOSS-TTS-Nano-100M. Shipping eSpeak-ng later, linked in or as a separate library beside the server, would be a new decision. The fork's Linux arm64 archives leave out ggml's CPU variants with SVE (`armv8.2_3`, `armv8.6_*`, `armv9.2_*`): on a Neoverse N2 they cut speech off or let it run on in 4 to 6 clips of 12, against 0 or 1 without SVE, deterministically for a seed, and audio.cpp has no SVE code of its own, so the cause is in the vendored ggml (fork `atomic/README.md`). Such a CPU loads `armv8.2_2`. Even so MOSS-TTS-Nano q8 ends a sentence early or runs on in about 1 clip of 20 on every platform measured (macOS CPU and Metal, 40 seeds), which the fork's smoke bounds but does not remove: a question for the catalog's choice of speech model. CI has no GPU, so CUDA and Vulkan builds are smoke-tested on the CPU backend only. Intel Macs get no build: the shared ladder offers none on x64 macOS. Windows CUDA archives are large (the cu12 companion carries cudart and cuFFT).
