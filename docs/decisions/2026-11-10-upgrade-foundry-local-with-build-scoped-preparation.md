# 2026-11-10 — Upgrade Foundry Local with build-scoped preparation

- **Context:** Foundry Local 2.4.0 ships as five archives repackaged by conf from Microsoft NuGet packages, with an additional pinned Intel OpenVINO 1.8.1 package for Windows x64. It requires C API 3 and, on Linux ARM64, glibc 2.34. Existing 2.1.0 installations, locally installed models and accelerator preparation must remain usable until an explicit update and after manual rollback.
- **Decision:** Accept the optional schema 1 `distribution: atomic-conf` only in the fixed conf release namespace; absence retains the Microsoft URL. Apply one host/core/API compatibility predicate to manifest candidates and offline active builds, retaining `minCoreVersion` in new install records. Negotiate API 3 before API 2 and require staging's actual library version and supported table to match the selected release before activation. Keep the legacy accelerator record exclusively for 2.1.0; new releases use `runtime/<tag>/<platform>/accelerators.json`. Capture the build for every preparation, model check and load. Add the optional model runtime minimum to the existing check route, comparing runtime versions numerically without a network request.
- **Consequences:** Linux ARM64 with glibc 2.28–2.33 stays on 2.1.0 even if 2.4.0 files are present. A failed staging probe leaves the previous session running. Successful activation may interrupt its response, as before; rollback remains unload plus removal of the new build. Old cores can still read the untouched 2.1.0 preparation record. Foundry's legacy parsed cache omits `schema_version`; only the cache reader restores that discriminator, while network parsing stays strict. Windows DLL search changes run only in the child host, retaining the build's dependencies and inherited PATH while adding CUDA/cuDNN bins through `AddDllDirectory` and `SetDefaultDllDirectories`. Preload Foundry with `LoadLibraryExW(DLL_LOAD_DIR | DEFAULT_DIRS)` before binding its symbols: otherwise a system ORT (1.17.1 on the acceptance host) can replace the bundled ORT and fail initialization with error 1114. A failed CUDA preparation does not block CPU or other accelerators. Real native probes are separate evidence from generation and hardware acceptance; consumer releases remain gated on their own qualification.
- **Windows NPU qualification:** The owner approved adding Intel.ML.OnnxRuntime.EP.OpenVINO 1.8.1 after the system WinML OpenVINO 1.8.95 EP failed on ORT 1.31.0 and 1.31.1 (`OrtEpApi_ReleaseEpContextConfig_SinceV28` unavailable). The same NPU model still generates with 2.1.0/ORT 1.30.0. Downgrading ORT alone is incompatible with GenAI 0.19.0, which needs ORT API 31. Preserve the three Microsoft packages and all signed native bytes; place Intel's Windows natives in `lib/openvino/` with its original license metadata and notices. Use a distinct `foundry-local-win-x64-openvino-1-8-1.zip` asset and retain the original published ZIP. Register the pinned plugin through standard ORT API 31 on its shared process environment. Acquire an environment reference lazily when OpenVINO is requested and release it after the Foundry manager. Do not accept WinML's registration as the bundled EP's readiness or fall back to the incompatible system plugin. Other EPs and 2.1.0 keep their paths. Missing Intel files do not block CPU probes or CUDA preparation. The new archive is 93,972,839 bytes, SHA-256 `23ce1fea75d64254e99042c3e99e1fc2bb0dd5befff07d4a013857920c67b2a1`; the NuGet catalog SHA-512 is pinned in conf. Production core and app-core both generated with the unchanged NPU-only model on Windows. A local download fixture exercised the production installer/hash/staging pipeline before remote publication was explicitly approved. The owner then authorized publication: the corrected archive is now public and its downloaded bytes match the recorded SHA-256. Conf's local candidate selects this asset for Windows x64 only. An audit preserved all five original asset IDs, digests, sizes and modification timestamps; the production manifest remains unchanged pending consumer releases.
- **Additional Mac acceptance:** Public 2.4.0 installation passes on macOS 26.6.2 ARM64, but ordinary core WebGPU preparation fails with `Manager_DownloadAndRegisterEps: unknown error`. The unchanged vendor C API reproduces the same failure in a typed C++ client with shared hosting disabled, without Bun FFI or a progress callback. The CDN download succeeds, and direct registration of its unchanged WebGPU 0.2.1 library in ORT 1.31 succeeds. A diagnostic host using that registration generates a real Qwen3.5 0.8B answer through Foundry 2.4.0/GenAI 0.19.0 (4096 context, 15 completion tokens, stop, exit 0). Early environment creation alone does not fix native preparation. The precise internal exception remains unknown; the ordinary Mac flow is not qualified. No production registration workaround or signing/security change was made. All 13 original model files and the isolated model copy remain unchanged after generation, apart from the explicitly reduced context in the copy before testing.
