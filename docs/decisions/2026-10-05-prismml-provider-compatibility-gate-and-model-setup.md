# 2026-10-05 — PrismML provider: a per-file compatibility gate and one recoverable model setup

- **Context:** [Use PrismML llama.cpp for desktop Bonsai](2026-10-05-use-prismml-llamacpp-for-desktop-bonsai.md) chose a separate `atomic-prism` provider. Implementing it raised five questions the direction left open: where the engine builds and the model rules come from and how they change without a release; how a Prism-only file is kept off the stock engines; how engine, model and projector are installed as one thing the app can follow, cancel and resume; how the app learns about new builds; and which core version carries it. The app pins the core's exact version (`CORE_VERSION_MISMATCH`), so a protocol capability flag is not needed.
- **Decision:**
  - **Engine source.** Builds come from `PrismML-Eng/llama.cpp` release URLs as conf `backends/atomic-prism-manifest.json` lists them, never a mirror in v1. Every asset needs `sha256` and `size`, and starts as `candidate`. Only `approved` assets are offered unless the user sets `allow_candidate_builds`. A `withdrawn` release, or one whose `min_core_version` is newer than this core, is never offered; a pack already installed from it is kept. The manifest is fetched from conf `main`, cached on disk, and backed by a bundled baseline. Install refuses an unlisted asset, merges the Windows `cudart-*` companion into the same `build/bin`, and requires `llama-server --version` to report the tag's build before the side-by-side rename. An update therefore never replaces the pack a running session uses.
  - **Updates.** `POST /backends/atomic-prism/updates` offers the newest approved, non-withdrawn build of the same backend family, compared by the build number in the `prism-b<build>-<sha7>` tag. The answer says why (`newer`, `withdrawn`, `model_requires` when the caller passes the build a model needs) and carries the release's `notes_url`, `notes` and download size for the app's banner. Conf's `prism-release-watch` workflow proposes new releases as `candidate`; only a person promotes them to `approved`.
  - **Compatibility per file, not per family.** A conf rule (`models/atomic-prism-models.json`, cached, with a bundled baseline) matched by sha256 or by repository and file decides first; otherwise the GGUF header decides (Prism tensor types, `prism.hadamard.*`, the legacy Q2_0 g128 packing). Every llama.cpp load, on all three providers, is checked inside the runtime before auto-unload and the GPU claim, from cached data only, so a load never waits on the network. A refused load leaves the user's current model loaded. There is no fallback from a Prism file to upstream or TurboQuant. The public server never auto-loads, so this one gate covers the control API and `/v1` alike. An unreadable header is let through: refusing it would break files that worked before.
  - **Model setup.** `POST /models/setup-plan` is a pure plan over the verdict, the rule, the manifest, the host and free space. Its `digest` covers what decides the work but not free space. `POST /model-setups` starts from that digest and refuses a changed plan with `MODEL_SETUP_PLAN_STALE` instead of doing something else. Records live one file per setup under `<data>/atomic-core/prism-setups/`, written atomically with a `.bak` copy and compare-and-set by revision. The instance lock makes this core the only writer, so no lock file is needed. A retried `request_id` returns its setup. One pack install is shared by every setup that needs it: cancelling one setup stops its wait, not the install. After the downloads, the header of the file on disk is the last word: a file that needs another engine than planned fails the setup rather than being registered. A setup selects the pack it installed in `atomic-prism`'s `version_backend`, writes `model.yml` (with `atomic_runtime`) last, and emits `model:imported`. A setup a stopped core left mid-way is `interrupted` at the next start, and `resume` plans it again from its request, reusing downloaded `.tmp` files. The Hugging Face token travels only in download headers.
  - **Version.** The core goes to **0.10.0**, the `min_core_version` the first manifest entry names.
- **Consequences:** New PrismML builds and new Bonsai packings reach users through conf without a core or app release, and only after we approve them. The gate reads at most a header's tensor table per load (bounded, `src/models/gguf/tensors.ts`). A manifest or rules file that breaks its schema is ignored in favour of the cache or the baseline, so a bad conf commit degrades to the previous behaviour instead of blocking loads. Candidate builds are offered to no one by default, so until a build is promoted, Bonsai setup on a given host answers `no_engine_build` unless that user opted in. Hardware acceptance (Metal, CUDA, Vulkan, ROCm/HIP) remains manual and is what promotes an asset. New data paths, routes, the event and the error codes are listed in `docs/contracts.md`.
