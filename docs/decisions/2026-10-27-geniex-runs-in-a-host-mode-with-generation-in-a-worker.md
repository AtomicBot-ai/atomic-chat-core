# 2026-10-27 — GenieX runs in a host mode of the core binary with generation in a Worker

- **Context:** Qualcomm's GenieX (v0.9.3, BSD-3-Clause) is the one source of a Microsoft-signed HTP bundle for the Hexagon backend of ggml: with it any Q4_0 GGUF runs on the NPU of a Snapdragon X laptop, and AI Hub bundles add the fastest NPU path. It is a native library with a C API (`geniex.h`), two plugins (`llama_cpp`, `qairt`) and no server of its own we could run: the Qualcomm CLI installs system-wide, unsigned, keeps models in its own cache and cannot be stopped over stdin. Every call of the C API is marked "not thread-safe"; `geniex_llm_generate` blocks the calling thread and calls the token callback in it; there is no cancel call, only `GENIEX_ERROR_COMMON_CANCELLED` when the callback returns `false`. Loading the library into the core would let a native crash take down `:1337`. Change `add-geniex-runtime`, design D1 and D6; the spike (S1–S5) is still to run on a Snapdragon X laptop, see the change's `rulings/core.md`.
- **Decision:** the host is a hidden mode of the same binaries, `atomic-chat-core geniex-host probe|inspect|serve` (and the app core's, and `atc`'s through `@atomic-chat/core/geniex-host`), started by the core with `process.execPath`, one process per model, as for Foundry Local and LiteRT-LM. Unlike those, the library lives in a Bun `Worker` of the host: `geniex/host/worker.ts` binds the C API through `ffi-bun.ts` (the third and fourth files in `src/` allowed to import `bun:*`), creates the model and runs `geniex_llm_generate` there; the token callback is a plain `JSCallback` run synchronously in that thread and posts each token to the main thread with `postMessage`; a cancel is one `Int32` in a `SharedArrayBuffer` the callback reads, so the library ends the generation with `CANCELLED`. The main thread keeps the HTTP server (`/v1/models`, `/v1/chat/completions`, stream and non-stream) and a FIFO of generations. The Worker's script is bundled by `scripts/build-geniex-worker.mjs` into a generated module (`host/worker-source.generated.ts`, not committed, built before `tsc` and before the binaries) and started from a `blob:` URL: a Worker named by a path inside a compiled binary fails on Windows with the Bun CI pins (1.3.10 reads `B:\~BUN\root\worker.js` from the disk; oven-sh/bun#16869, #29124, fixed in 1.4.1), and a blob needs no path anywhere. The host reads tool calls (`<tool_call>…</tool_call>`, and fenced JSON when tools were asked) and thinking (`<think>…</think>`) out of the token stream itself, turns `response_format` into a GBNF grammar (`host/grammar.ts`) for the sampler, and writes request images to files under the host's `tmp` for the VLM. `inspect` reads a GGUF header or a bundle's `genie_config.json`, `metadata.json` and HTP config without the library (AI Hub bundles carry no `geniex.json`; spike S4, 2026-10-28).
- **Consequences:** a library crash ends one host's Worker and process; the core reports `session:died`. The "not thread-safe" C API is honoured literally: one thread calls it. Requests to one model queue; `GET /v1/models` never waits. Each model costs two JavaScript threads in one process (about 60–100 MB). No conversation pool: every request is a full prompt (the NPU prefill is fast; KV save/load of the C API is a later option). The struct layouts in `ffi-bun.ts` follow the v0.9.3 header for a 64-bit target and are unverified until the spike; so is the Worker's synchronous callback under Bun on Windows arm64 — the fallback of design D1 is a native host in C with the same protocol, which would replace `worker.ts` and `ffi-bun.ts` alone. The e2e tests of this repository run with `ATOMIC_GENIEX_TEST_CHIP` and a fake host, since no CI machine is a Snapdragon.
