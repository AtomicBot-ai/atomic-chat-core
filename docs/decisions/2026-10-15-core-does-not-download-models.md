# 2026-10-15 — The core does not download model files; clients do

- **Context:** model files were downloaded in two places at once. The app downloaded ordinary GGUF files and the managed engines' models itself, but Bonsai went through the core's model setup (`/model-setups`). `atc` sent every GGUF through the same setup and downloaded its media and MLX models with the `Downloader` exported as `@atomic-chat/core/downloads`, in parallel ranges (`downloadStreams`). So the core kept two model download paths, each with its own records, crash recovery and failures. One example: parallel ranges needed twice the file's size on disk at their peak, more than the preflight checked, and a cancel during the merge left `.segments/` behind. Neither path was the only one. The managed engines already followed the rule that clients download models (spec `tensorrt-llm-models`). Change `remove-model-downloads-from-core` extends it to every model.
- **Decision:** the core downloads engine builds only. It no longer downloads model files, from the control API, at startup, or from its own CLI.
  - **Removed:** `POST /models/setup-plan`, `/model-setups` and `/model-setups/:id[/cancel|/resume]`, the `model-setup:changed` event, the snapshot's `model_setups`, `MODEL_SETUP_PLAN_STALE` and `MODEL_SETUP_NOT_FOUND`, the six model setup methods of `@atomic-chat/core/client`, `downloadHfModel` from `./models`, `AtomicCoreOptions.downloadStreams` with `downloads/segmented.ts` and the 250 ms progress cadence, the `./downloads` subpath, and the `ATOMIC_HF_ENDPOINT` test hook.
  - **Kept:** `POST /models/compatibility`, before download (repo and file) and after it (`model_id`, read from the file on disk), and `GET /models/atomic-prism/families`. Together with `/backends/:p/{catalog,recommendation,install}`, `/engines/:e/builds/:v/:variant/activate` and `/disk/available`, they give a client everything it needs to plan a Bonsai download. The compatibility gate on every llama.cpp load is unchanged, so a file the client did not check is still refused when it is loaded. The `Downloader` stays as an internal module for engine installs, with one stream and progress every 10 MiB, and its `snapshot()` still feeds the snapshot's `downloads`.
  - **Startup:** `<data>/atomic-core/prism-setups/` is removed and none of its setups resumes. Partial `.tmp`/`.url` files next to the models are left for the client that downloads the model again.
  - **CLI:** `atomic-chat-core serve owner/repo` with no such model on disk exits with `MODEL_NOT_FOUND` and says to download it first, before it starts an owner and without a network request. `--select`, which picked a quantization to download, is accepted and ignored, so an old script reaches that error rather than a parse error.
- **Consequences:** a breaking release, `0.17.0`. An app or `atc` built against 0.16 that still calls `/model-setups` gets 404. Both pin the core's exact version (`CORE_VERSION_MISMATCH`), so the new core only arrives with a client that no longer calls it. The order is core first, then app and `atc`. A setup that was cut off by the upgrade is lost as a record. Its partial files stay, and the client resumes them only if its sidecar format matches the core's. Without a match it downloads them again. The core no longer contacts Hugging Face for model files, only for headers (compatibility) and the catalog.
- **Owner:** `team`.
