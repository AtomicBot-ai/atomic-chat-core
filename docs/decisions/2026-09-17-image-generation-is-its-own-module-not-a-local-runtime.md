# 2026-09-17 — Image generation is its own module, not a local runtime

- **Context:** The app's image-generation line (v2.0.38–2.0.40) supervises one resident `sd-server` (stable-diffusion.cpp) from a Rust plugin, `tauri-plugin-atomic-diffusion`: it loads a model, runs jobs against `/sdcpp/v1/*`, parses the step bar out of the process output, and owns the gallery on disk. The core migration deleted the app's Rust inference, so that backend has to live here. The obvious home, a fifth `LocalRuntime` under a new `LocalProviderId`, is the wrong one: the provider id is a pinned contract with the app (settings, events, model claims), and everything registered in `runtimes` flows into `/sessions`, the snapshot, `/v1/models`, the router and chat auto-unload. An image model is not a chat model and must not be offered as one. `SidecarTable` is no closer: it emits `session:*` and has no notion of a spec that outlives its process.
- **Decision:** `src/diffusion/` is a module of its own with one service object. It keeps exactly one resident session and the spec that started it, which survives a cancel or a crash so the next job respawns the server without the app repeating the load. It has its own events (`diffusion:state`, `diffusion:progress`, `diffusion:job`, `diffusion:error`) and its own control routes under `/atomic/v1/diffusion/*`. From the runtimes it borrows only process mechanics: `spawnManaged`, `randomFreePort`, `buildProcessEnv`, the raw-socket HTTP client, and the process journal, where its record carries `provider: 'diffusion'` so a crashed core's `sd-server` is reaped like any other child. Configuration stays in memory, as it did in the plugin: `PUT /diffusion/config {dataFolder, outputDir?, idleUnloadSecs?}`, where `dataFolder` must be the core's own data folder (anything else is `NOT_CONFIGURED`); the app sends it again on every `snapshot`, because a new core generation has forgotten it. The core adopts the app's existing paths, it does not invent any: `<data>/diffusion/{backends,models,scratch}` and `<data>/images` as the default output folder (a user-chosen output folder may be anywhere). Downloading the engine archive and the model files stays in the app (`download_files` + `decompress` survive there); the core finalizes an unpacked tree, lists and removes.
- **Consequences:** Image models never appear in `/v1/models`, `/sessions` or the snapshot, and the chat auto-unload policy does not know `sd-server` exists: freeing the GPU before an image load remains the app's job, as it was. Diffusion status is not part of the snapshot; the app reads `GET /diffusion/status` after each one. A headless install of the engine or a model is out of scope until the core downloads them itself. Shutdown has one more step: the public server stops, then the diffusion session, then the runtimes.
