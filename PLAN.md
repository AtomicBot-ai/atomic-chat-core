# PLAN.md — extracting the Atomic Chat inference core into `atomic-chat-core`

The single project document: where we come from, what we decided, how the core is built, in what order the app migrates,
and how we verify it. Sections 1–7 are the plan. Section 8 is the original port spec; its facts are reconciled against the current app code.
Compatibility means preserving behavior, formats and meaningful fields; comparison rules and allowed differences are in §5.1.
This is the target state, not a readiness report: implemented checks and gaps are tracked in `docs/testing-critical-flows.md`.

Conventions: `<data>` is the app data folder (macOS `~/Library/Application Support/Atomic Chat/data`,
Windows `%APPDATA%\Atomic Chat\data`, Linux `~/.local/share/Atomic Chat/data`). Paths like `src-tauri/...`,
`web-app/...`, `extensions/...` refer to the app repository `../Atomic-Chat`. Paths like `src/...`, `test/...` refer to this repository.

**Stage 4 revision (2026-09-17):** the [ADR on separating the owners](docs/decisions/2026-09-17-isolate-app-and-cli-owners.md)
replaces the shared folder/owner, the cross-scope settings migration and the detach on full app exit described below.
The CLI uses a separate `<system data>/atomic-chat-cli/data`, the app uses the former `<data>`; the app owner binary
`atomic-chat-app-core` lives only until the app fully exits or its registration expires, the CLI owner until an explicit shutdown.
Historical journal entries are kept as evidence of the former plan, not as current acceptance criteria.

## 0. Working order and journal

**How we move.** Iteratively, one small step at a time: a step is picked from the current stage in §4, formulated before starting
(what we do, what we do not touch, how we verify), executed, verified with `npm run verify` (for `src/runtime/` also `test:e2e`
on your own OS), and only then recorded below. **Checkpoint with a report to the owner happens when a stage closes**, not after every step: within a stage
steps run back to back without stopping, each with its own journal line. The stage report covers: what was done, what was found, what was not done
and why, the exit criterion with the verification result. Stopping inside a stage happens only if a step requires an owner decision
(a new dependency, a change to a decision in §2/§3, an ADR). Do not start a module until the previous one is green. Each journal entry is one line: date, step, result, link
to the verification. If a step changes a decision from §2 or §3, first the ADR, then the code.

## 1. Context

### 1.1 What exists now

Atomic Chat is a Tauri + React app (a fork of Jan) that runs local LLMs and serves an OpenAI-compatible API at
`localhost:1337/v1`. The "launch and configure inference" logic is cut along a language boundary and duplicated three times:

| Layer | Where | Size | Problem |
| --- | --- | --- | --- |
| Policy: backend choice by hardware, `model.yml`, 34 provider settings, context fitting, speculative drafts | `extensions/llamacpp-upstream-extension/src/index.ts` (+ the `llamacpp-extension` clone, + `mlx-extension`) | 10k + 7.5k + 3.3k lines of TS | runs **inside the webview**, tied to `invoke`, `localStorage`, the `@janhq/core` event bus |
| Mechanics: spawning `llama-server`, arguments, readiness, `--list-devices`, GGUF, resumable downloads | `src-tauri/plugins/tauri-plugin-{llamacpp,llamacpp-upstream,mlx,foundation-models,hardware}` | ~26k lines of Rust | two plugins are clones; everything is tied to Tauri commands |
| Cloud and proxy: providers, keys, the "model → provider" router, Responses↔Chat shims, ChatGPT OAuth | `web-app/src/lib/model-factory.ts`, `src-tauri/src/core/server`, `src-tauri/src/core/auth` | 4k TS + 11k Rust | keys in the webview's `localStorage` + an in-memory mirror in Rust |
| CLI | `src-tauri/src/bin/jan-cli.rs`, `src-tauri/src/core/cli` | 2.6k Rust | a third, cut-down implementation of the same policy for a single provider |

None of the layers is reusable outside the app.

### 1.2 Goal

A standalone TypeScript package `atomic-chat-core` (this repository) that owns local **and** cloud
inference and the OpenAI-compatible server. Consumers:

1. **CLI** — a single binary from this repository.
2. **The Tauri app** — a client of a local core process shipped together with the app.
3. **External OpenAI clients** — Codex, Claude Code, OpenCode, curl.
4. **TS programs** — as a library.

The app migrates to the core in stages within this plan; the Rust inference plugins and the Rust proxy are removed last.

**The boundary of this migration is desktop:** macOS, Windows x64, Linux x64. iOS/Android keep the necessary Rust implementation
and separate build checks. Migrating mobile and removing its execution path require a separate plan.

## 2. Decisions made

| # | Decision | Reason |
| --- | --- | --- |
| 1 | Language — **TypeScript**, not Rust | the policy is already in TS; the Rust mechanics are thin and well specified (§8.2) |
| 2 | **Bun** for packaging and running the compiled binary; **code within the Node-compatible API**: `node:*`, no `Bun.*`, no native addons | reduces runtime lock-in; Node SEA is a candidate fallback path, not a confirmed one-line replacement |
| 3 | v1 backends — **all four**: `llamacpp-upstream`, `llamacpp` (turboquant), `mlx`, `foundation-models` | owner decision |
| 4 | Cloud, router and the `:1337` HTTP server — **in the core**; the Rust proxy is removed last | the only place that knows all providers, keys and sessions |
| 5 | **Order: local runtime, control and process ownership → CLI → app adapter → public server and cloud** | a minimal control API and attach are needed before shipping the CLI; the session mirror preserves the Rust agent's direct path |
| 6 | `jan-cli` is replaced by the TS CLI: the file name `resources/bin/jan-cli` stays, the content is a copy of the `atomic-chat-core` binary | the name is load-bearing (the app's AGENTS.md §4); one binary dispatches by subcommand |
| 7 | **Control `/atomic/v1/*` + SSE separated from the public `/v1`; the app and the CLI own different instances** | stop/start of the public API does not disable control; a full app exit terminates only app-core, a CLI command leaves the daemon alive |
| 8 | **Data isolation**: the app keeps `<data>`, the CLI uses `<system data>/atomic-chat-cli/data` | models, settings, keys, lock and state-file do not overlap; neither migration nor automatic copying |
| 9 | New core files only under **`<data>/atomic-core/`** | one new data folder, formalized with an ADR in the app |
| 10 | Hardware: shell probes + `--list-devices` in the core; the app **injects** exact NVML/Vulkan data via `PUT /atomic/v1/hardware/override` | without native addons there is no NVML; `tauri-plugin-hardware` stays |
| 11 | ChatGPT OAuth moves to the core at the server stage; callback port 1455 is fixed; exactly one writer of tokens and refresh | switching the server includes handover of auth ownership, cancelling the old callback and stopping the old refresh |
| 12 | AI SDK in the core only `ai` + `@ai-sdk/openai-compatible` for `atomic-chat-core/client`; the server forwards cloud requests as raw bodies with key substitution | this is what `proxy.rs` does; the app already sends provider-native bodies |
| 13 | External dependencies: `yaml`, `tar`, `yauzl`, `ai`, `@ai-sdk/openai-compatible`; CLI parser — `node:util.parseArgs` | everything else is `node:*` |
| 14 | No `jan*` identifiers; `atomic-*` | app rule |
| 15 | Rust traps (§8.2): Windows `PATH` with CUDA is **fixed** (prepend); `parseBackendVersion("b10018-1.3.0")=0` is **reproduced** until the app leaves the Rust plugins | the first is a bug with no dependents; the `verify_backend_binary` gate hangs on the second |
| 16 | Tests: unit tests next to the code, contract fixtures from Rust, e2e on the compiled binary, app-e2e against the Tauri app, live via env | AGENTS.md §5; crashes, reconnection, two clients and migration are verified before the corresponding stage is enabled |

**Owner and clients.** One core process per canonical data folder. The app and the CLI first check the owner
and the protocol version, then attach; if there is no owner they launch `daemon --control-port 0` and retry the attach.
`AtomicCore.create({role:'auto'})` follows the same rules; `role:'owner'` on an occupied folder returns `CORE_ALREADY_RUNNING`.
The lock is acquired exclusively; a PID without a launch identity is insufficient because of PID reuse. After
creating the lock exclusively, the owner publishes the endpoint atomically; the client waits for the handshake to complete. Stale lock recovery
is serialized too: two starting clients cannot replace the owner at the same time. Unreachable HTTP with a live process
does not permit removing the lock or launching a second core. The concrete inter-process mechanism is verified on three OSes before stage 2.

The owner holds control, its sessions and downloads; the public server is enabled separately. App exit, stdin EOF
or a CLI client finishing do not stop the core. `server stop` turns off only the public listener; `shutdown` is an explicit
stop of the whole core with all sessions, with a check for other active clients and a separate `force` for a forced stop.
Clients register with a heartbeat and an expiry; closing a client removes its registration but does not unload its models.
v1 has no automatic idle shutdown. `--standalone` is allowed only with an explicitly specified separate data folder.
With an incompatible version of the live owner — a clear refusal, without a second core or automatic killing; updating
the binary requires an explicitly stopped owner (on Windows the executable of a running process cannot be replaced).

**Coexistence with legacy.** Until the full migration, the Rust plugins are not considered participants of the core lock.
Before the CLI ships, the app introduces a shared inter-process guard for the legacy runtime and for changes to shared models/backends.
A core client does not launch or change a resource while legacy owns it; an owner transition requires operations to finish and an unload.
The model roots of the two llama.cpp providers are shared: delete/import protection applies to the shared path, not only to the provider id.
App versions without this guard do not support running simultaneously with the new CLI on the same folder; on detecting
such an app, the CLI rejects mutating operations. A downgrade is done after an explicit core stop.
The reaper first checks for a live owner and the journal, excludes its processes, and only then cleans up confirmed orphans.

**Settings migration — before the first core-load.** The import is versioned and runs separately for each provider and for
server/cloud; the runtime switch is not enabled until its import is confirmed. At the legacy stage the source of truth is
`localStorage`, after the resource is handed over to the core — the core's file. `settings.json` stores a monotonic revision and, for each migration
area, a baseline snapshot, a hash of the imported legacy state and the last confirmed revision of its mirror.
The API accepts `expected_revision`, applies the write atomically and returns a conflict on a stale revision.

The app mirrors confirmed core changes into `localStorage` and confirms the revision; on connecting it receives
a full snapshot, so CLI changes made while the app was closed are not lost. An identical repeated import returns the previous
result, not an unconditional `ALREADY_MIGRATED`. If the legacy copy has changed since the confirmation, it is compared
against the baseline snapshot: one-sided/non-overlapping edits are merged, a conflict on a single field requires a user choice
before switching that area. Automatic choice by file time is forbidden.

Before a planned rollback the app confirms that the legacy mirror is up to date and hands ownership back. A rollback without this
step does not promise fresh settings in the old UI; the new core keeps its data and resolves divergences on the next launch.
Nothing is deleted before stage 6; a single `migrated` flag is not enough for cleanup. `model-provider` also contains the model
catalog and UI state: only migrated fields are deleted, after verifying all remaining readers, not the whole zustand store.

### 3.5 Events

Internally — a typed `EventEmitter`. Catalog (`src/contracts/events.ts`):

| Group | Events |
| --- | --- |
| download | `download:started`, `download:progress` (every 10 MiB), `download:error`, `download:stopped`, `download:verified` |
| model | `model:validation-started`, `model:validation-failed`, `model:imported` |
| backend | `backend:download-started`, `backend:download-finished`, `backend:manual-downloading`, `backend:manual-failed`, `backend:better-detected`, `backend:runtime-reported` |
| session | `session:started`, `session:died`, `session:ctx-increased`, `session:unloaded` |
| other | `settings:changed`, `server:started`, `server:stopped`, `server:bind-failed`, `api:request`, `core:log` |

Across the process boundary: the only event channel is `GET /atomic/v1/events` (SSE, `id: <instance_id>:<seq>`, replay from a ring of 1000).
`GET /atomic/v1/snapshot` returns sessions, downloads, settings revisions and the public server state together with a consistent
cursor. The client applies the snapshot and subscribes after the cursor; on ring overflow or a different `instance_id` the server
requires a resync. Duplicate events are dropped by id. stdout carries only the ready line at startup; logs go to stderr/file.
The Rust bridge re-emits them as Tauri events `atomic-core://<name>`; `CoreEventBridge` in web-app maps them onto 17 legacy names
(`onFileDownloadUpdate`, `onBetterBackendDetected`, `download-<taskId>`, …), existing listeners do not change.

### 3.6 Local owner protocol

| Phase | Mechanics |
| --- | --- |
| Spawn/attach | look for a compatible owner; otherwise `atomic-chat-core daemon --data-folder … --resources-dir … --control-port 0`; a standalone process without `kill_on_drop`, independent of parent PID/EOF; Windows `CREATE_NO_WINDOW`. The owner creates the token under the lock; clients read the protected file |
| Readiness | the first stdout line `{event:"core:ready", pid, instance_id, protocol, version, control_host, control_port}` and an authorized health check ≤ 15 s; ready means control is ready, not models or the public API. After bootstrap the pipes are closed/detached without stopping the core |
| Operation | snapshot + SSE; Rust sets `AppState.local_server_endpoint` only from the state of an actually running public server, including the actual host/port/prefix. The control port is never substituted as an inference endpoint |
| Crash | clients immediately invalidate the mirror of the dead `instance_id`; errors of in-flight requests are explicit. Restart via the shared lock with backoff 1/5/15 s (≤ 3 in 5 min); only one client becomes the launcher. A failed bootstrap may be terminated only after confirming the identity of the launched process |
| Recovery | the new owner terminates confirmed orphans from the journal, then publishes a new `instance_id`; sessions are not restored automatically, the snapshot is empty for dead sessions. Downloads become interrupted and are resumed explicitly from verified `.tmp/.url`; automatic retry of generation is forbidden |
| Client exit | detach and heartbeat stop; the core and models keep running. On the next launch the app attaches, it does not reap a live owner |
| Shutdown | `POST /atomic/v1/shutdown` checks for other clients, blocks new operations, finishes downloads and backend processes, turns off both listeners, releases the lock last. Emergency termination is a separate explicit action with a PID/start identity check |

Auth: `/v1/*` — as today (`Bearer`/`X-Api-Key`, trusted hosts, CORS). `/atomic/v1/*` — always `Bearer <control_token>`,
a separate bind on loopback only, Host and peer checks; browser access via CORS is disabled. The webview calls
Rust `atomic_core_call`/relay, so the control token never reaches JS and the dev origin needs no exceptions. The CLI uses HTTP
directly. `client/` stays browser-safe, but accepts a transport: fetch for headless clients or an injected invoke for Tauri.
File permissions are verified on each OS: `0600` on Unix, access for the current user via ACL on Windows.

Control routes: `health`, `snapshot`, `events`, `clients/*`, `shutdown`, `server/*`, `models/*`, `sessions/*`, `models/:p/:id/{load,unload,capabilities,speculative/ensure}`,
`gguf/{validate,support}`, `tokens/count`, `embed`, `backends/:p/*`, `hardware/{info,usage,devices,override}`, `settings/{:p,server}`,
`cloud/providers/*`, `auth/chatgpt/*`, `downloads/*`, `transcription/*`, `migrate/legacy-storage`.
Errors — `{error:{code,message,details?}}`; the client throws `AtomicCoreError`, error handling in the app does not change.

## 4. Stages

Flags: `ATOMIC_CORE_CMD` (dev: run the core from sources), `atomic_core.runtime` in `<data>/store.json` (`off | llamacpp-upstream | all`),
`atomic_core.server` (`legacy | core`), env overrides `ATOMIC_CORE_RUNTIME`, `ATOMIC_CORE_SERVER`. Rust reads both into `AppState`
and hands them to the webview via the `get_atomic_core_flags` command.

Switching the runtime is an ownership handover after operations finish, the corresponding sessions are unloaded and settings
are synchronized; not a hot swap of the selector underneath a running model. Allowed combinations: `server=legacy` with any runtime;
`server=core` only with runtime `llamacpp-upstream|all` and a working bridge for all remaining legacy providers. Anything else is rejected
before the state changes. Mobile always keeps the legacy path. `ATOMIC_CORE_CMD` sets the launcher (`node/bun …/main.ts`),
without a subcommand: the app appends `daemon` and the arguments exactly once.

## 7. ADRs in the app's `docs/decisions/`

1. The inference core is extracted into a separate TS repository `atomic-chat-core` (Bun binary, Node-compatible API).
2. Migration order: runtime/control/ownership → CLI with legacy guard → adapter → public server; desktop legacy is removed last, mobile is kept.
3. Wire contracts are pinned with Rust fixtures with explicit comparators and normalization of dynamic fields.
4. Two resources `resources/bin/atomic-chat-app-core` and `atomic-chat-core` from one version, independent app/CLI owners; separate control/public listeners, SSE + snapshot, bootstrap via stdout.
5. The `jan-cli` file name is kept; the content is a copy of the compiled `atomic-chat-core`.
6. The owner binary is signed with hardened runtime and JIT entitlements on macOS; the final universal artifact runs on both architectures.
7. The exact core version is pinned in the app; a protocol/version mismatch is rejected at handshake.
8. The reaper accounts for the owner and launch identity; a shared guard protects legacy/core resources before the CLI ships.
9. Core-owned sessions are mirrored into `AppState.core_sessions`; the agent keeps talking to `llama-server` directly.
10. llama.cpp extensions become thin adapters under the legacy `@janhq/*` names; legacy code stays in the package until removal.
11. Settings migrate area by area before the first load, with revisions, a confirmed mirror and conflict resolution on downgrade.
12. `start_server` in Rust coordinates the handover of the public API and the state-file writer; the control API runs independently.
13. Provider configs and keys live in the core (`credentials.json` 0600); `register_provider_config` goes away.
14. Auto-increase-ctx collapses into the core.
15. Local API server telemetry stays in Rust and is fed by `api:request` events.
16. Hardware: probes in the core, NVML/Vulkan override from the app.
17. CLI `serve` connects only to the CLI owner; the command's exit does a detach, stopping the CLI core is explicit. A full app exit stops app-core.
18. The CLI `launch` catalog is ported to TS; the Launch page stays on Rust `configure_*`.
19. New data folder `<data>/atomic-core/`.

### 8.2 Rust mechanics (`src-tauri/plugins/tauri-plugin-llamacpp-upstream/src/`)

**Spawn** (`commands.rs:66-381`). `backend_path` is the full path to the binary. `-m` and `--mmproj` are validated; on Windows non-ASCII paths
are converted to 8.3 (except shards `*-NNNNN-of-NNNNN.gguf`). Env: `LD_LIBRARY_PATH` / `DYLD_LIBRARY_PATH` / `PATH` + `cwd` = the binary's directory;
CUDA directories (`utils/src/system.rs:150-340`): Linux — `CUDA_HOME|CUDA_PATH`, `/usr/local/cuda*`, `/opt/cuda`, `/usr/lib/x86_64-linux-gnu[/nvidia]`;
Windows — `CUDA_PATH\bin`, `CUDA_PATH_V*\bin`, `ProgramFiles\NVIDIA GPU Computing Toolkit\CUDA\*\bin`. `binary_requires_cuda` — `ldd` or a byte scan.
Windows flags `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`; `kill_on_drop`.

**Readiness.** A stdout/stderr line, lowercased, contains `listening on` | `all slots are idle` | `starting the main loop` | `http server listening`
**or** `GET /health` → 2xx (poll 200 ms, request timeout 500 ms). Early exit → classification; tick 50 ms; timeout → kill + `MODEL_LOAD_TIMED_OUT`.
Crash watcher 500 ms → event `local_backend://llamacpp_upstream_session_died` `{model_id, pid, error_code, message}` (`error_code` is the variant's Debug name).

**SessionInfo.** `{pid, port, model_id, model_path, is_embedding, api_key, mmproj_path?, runtime_device?}`. `api_key` = base64(HMAC-SHA256(secret, model_id)),
secret `'JustAskNow'` (`index.ts:531`), passed to the process as `LLAMA_API_KEY`. Port — random 3000–3999 with a bind probe.

**Unload.** SIGTERM → 5 s → SIGKILL (unix; 2 s on app exit); `TerminateProcess` (Windows x64; on Windows ARM64 there is no path);
unknown pid → `{success: true}`.

**Errors** (`error.rs`). Format `{code, message, details?}`. Cascade of stderr substrings **in order**:

| Substrings (lowercased) | Code |
| --- | --- |
| `dyld` + `symbol not found` | `OS_VERSION_UNSUPPORTED` |
| `out of memory`, `failed to allocate`, `insufficient memory`, `erroroutofdevicememory`, `kiogpucommandbuffercallbackerroroutofmemory`, `cuda_error_out_of_memory` | `OUT_OF_MEMORY` |
| `error loading model architecture`, `unknown model architecture`, `error loading model hyperparameters`, `key not found in model` | `MODEL_ARCH_NOT_SUPPORTED` |
| `unknown projector type` | `MULTIMODAL_PROJECTOR_LOAD_FAILED` |
| `corrupted or incomplete`, `invalid magic`, `wrong number of tensors`, `unexpectedly reached end of file`, `failed to read tensor` | `MODEL_FILE_CORRUPT` |
| otherwise | `LLAMA_CPP_PROCESS_ERROR` |

Crash: Windows `0xC0000005 / 0xC00000FD / 0xC0000409`, signals 11 / 6 → the text "crashed unexpectedly … MTP". Empty stderr → try stdout.

**Args** (`args.rs:239-342`), emission order:

1. `--no-webui` (not `ik*`); `--jinja`; `-m <path>`
2. `--cpu-moe`; `--n-cpu-moe N` (>0); `--override-tensor V` (non-empty)
3. `--mmproj <path>` [+ `--no-mmproj-offload` if `!offload_mmproj`]
4. `-a <model_id>`; `--port N`; `--chat-template V`
5. `-ngl N` (`n_gpu_layers` ≥ 0 and ≠ 100, otherwise `-1`)
6. `--threads` / `--threads-batch` (>0); `--batch-size` (≠ 2048); `--ubatch-size` (≠ 512)
7. `--device V`; `--split-mode V` (≠ `layer`); `--main-gpu N` (≠ 0)
8. flash-attn: `ik*` → bare `-fa` only when `on`; otherwise the string form `--flash-attn <auto|on|off>` for turboquant or build ≥ b6325; legacy — bare `--flash-attn` when `on`
9. `--context-shift`; `--cont-batching`; `--no-mmap`; `--mlock`; `--no-kv-offload`
10. `--parallel N` (>0) + `-kvu` when N == 1
11. MTP/DFlash: DFlash wins when both are set. Gemma (`mtp_draft_path`): `--model-draft P --spec-type draft-mtp --spec-draft-n-max 4` when build ≥ b9553.
    Qwen built-in: `--spec-type draft-mtp --spec-draft-n-max 2` when ≥ b9180. DFlash: `--model-draft P --spec-type draft-dflash --spec-draft-n-max <n_max|15>`
    only when `dflash_spec_supported` (probe `-h`).
12. `--metrics`
13. reasoning-preserve: `--reasoning-preserve` when `true` and ≥ b9837; `--no-reasoning-preserve` when `false` and ≥ b10762
14. embedding: `--embedding --pooling mean`; otherwise `--ctx-size N` (only if `!fit`), `--n-predict N`, `--cache-type-k` (≠ f16),
    `--cache-type-v` (only when `flash_attn ≠ off`, ≠ f16/f32), `--defrag-thold` (≠ 0.1), rope (`--rope-scaling` ≠ none, `--rope-scale` ≠ 1,
    `--rope-freq-base` ≠ 0, `--rope-freq-scale` ≠ 1)
15. fit (not `ik*`): `--fit on|off` [+ `--fit-ctx` ≠ "4096", `--fit-target` ≠ "1024"]
16. `extra_args` — POSIX splitter (quotes, `\` escaping; an unclosed quote → the whole string is dropped), appended **last**

Pre-pass: `concurrent_mode` → `parallel = max(slots, 2)`, `cont_batching = true`, `expose_metrics = true`; Vulkan → `flash_attn auto → off`.
Cache type whitelist `f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1`, anything else → `q8_0`; **the turboquant provider allows `turbo*`**.
`version_backend` without `/` → `INVALID_ARGUMENT`. `parse_build_number("b10018-1.3.0") = 10018`. `is_turboquant` = prefix `turboquant-` or `b<d>-<d>.<d>.<d>`.

**Runtime device** (`runtime_device.rs`). Parses `load_backend: loaded X backend`, `offloaded N/M layers to GPU`, `offloading N repeating layers`,
`<prefix>: LABEL model buffer size = V UNIT`; initialization errors: `failed to initialize CUDA`, `no CUDA devices found`, `error while loading shared libraries`,
`failed to load backend`, `ggml_vulkan: No devices found`, `no usable GPU found`. `primary_device` = the largest non-CPU buffer, if offloaded ≠ 0.

**`--list-devices`** (`device.rs`). The section after `Available devices:`; line `ID: Name (… MiB, … MiB free)` — the last parenthesis with `MiB` + `free` + `,`;
timeout 30 s; `DeviceInfo {id, name, mem, free}` in MiB.

**GGUF** (`gguf/`). Only the metadata KV block (strings ≤ 1 MiB, arrays ≤ 24 stringified); the tensor table is not read — nextn/MTP detection is in TS `util.ts`.
KV estimate from `{arch}.block_count`, `head_count_kv|head_count`, `key_length/value_length | embedding_length/head_count`, `context_length`, `sliding_window`;
bits: f32 32, f16/bf16 16, q8_0 8.5, q5_1 6, q5_0 5.5, q4_1 5, q4_0/iq4_nl 4.5, turbo4 4, turbo3 3, turbo2 2, anything else 16.
`is_model_supported` → RED/YELLOW/GREEN; `RESERVE_BYTES = 2 288 490 189` per pool; integrated = `vulkan_info.device_type == "IntegratedGpu"`;
no GPU → unified memory. HTTP reading in 2 MiB chunks, cap 120 MiB.

**Downloads** (`core/downloads/`). `save_path` is relative to the data folder and inside it. Sidecars `.tmp` + `.url`; resume only with `resume=true` and a matching URL.
`Range` → 206 + `Content-Range` check (start, end < total, total == expected); 200/416 → restart from zero; 408/429/5xx are retried;
5 retries, reset after every 1 MiB of progress. Event `download-<task_id>` `{transferred, total}` every 10 MiB (cumulative per task);
`onModelValidationStarted {modelId, downloadType: "Model"}`. sha256 + size after all files; on failure, deletion of the file and, **non-recursively**, its folder.
Headroom 512 MiB; HEAD preflight 30 s × 5; Windows path ≥ 260 → error; per-item proxy (`http|https|socks4|socks5`, `no_proxy`, `ignore_ssl`); cancel deletes nothing.
Tags `[disk_full | disk_permission | disk_file_locked | disk_path_too_long | disk_device_lost | disk_io]` — the `web-app/src/lib/telemetry.ts` contract.

**Data folder** (`core/app/commands.rs`). `data_dir()/<APP_NAME | "Atomic Chat">/data`; `settings.json` `{data_folder, autostart_preference}` is looked up in
`config_dir/<pkg>` (Linux, if present) → `data_dir/<pkg>`; legacy `Atomic-Chat` is preferred over `chat.atomic.app` if it exists.

**Archives** (`core/filesystem/commands.rs:334-515`). Only `.tar.gz` and `.zip` (zip-slip guard, unix mode); `normalize_backend_layout` → `build/bin/<exe>`.

**MLX** (`tauri-plugin-mlx`). Binary `resources/bin/mlx-server`. Args: `--model <dir> --host 127.0.0.1 --port N`, `--max-kv-size`,
`--draft-model <dir> --draft-kind <dflash|mtp|eagle3> --draft-block-size`, `--kv-bits F --kv-quant-scheme S` with `uniform|turboquant`.
Env `MLX_VLM_SINGLE_MODEL=1`. Readiness only via the log: stdout — `uvicorn running on, application startup complete, http server listening,
server is listening, server started, ready to accept, server started and listening on`; stderr — `uvicorn running on, application startup complete,
server is listening, server listening on, server started and listening on`. One load at a time. `api_key ""`; `model_path` = the directory.

**Foundation Models** (`tauri-plugin-foundation-models`). Binary `resources/bin/foundation-models-server`; args `--port N [--api-key K]`;

`GpuInfo {name, total_memory, vendor, uuid, driver_version, nvidia_info:{index, compute_capability}|null, vulkan_info:{index, device_type, api_version, device_id}|null}`;
